# Visual study before implementation

Use when the user asks to develop the visual idea first, study live references, or diagnose repetitive generated compositions. Ordinary narrow edits and task-first builds do not need this extra stage.

## Establish what was seen

Use an available browser to inspect one or two relevant live pages at desktop and phone sizes. If the native session cannot browse, a host may capture those pages and pass the images to its image-capable reader. Distinguish direct browsing, viewing host captures, reading source text, and reading annotations. A skill installed for a browser is not evidence that a working browser tool is configured. If no image-capable path works, report visual study pending; do not fabricate visible observations.

Record the source URL, capture date, viewport and a few concrete visible decisions. Identify a limitation or tradeoff. Mark emotional interpretation as interpretation. Keep this receipt brief; do not copy source marketing text or produce a story about the designer's private intentions.

## Make a visual proposal

Use supplied asset filenames or an asset manifest. If a path is missing, obtain one bounded directory listing or ask the host for a manifest rather than guessing font filenames repeatedly. Use the project's real material and content to create a small runnable composition before implementing the full interaction system. Preserve enough content to judge hierarchy and rhythm below the fold. Label intentionally pending interactions. Study how type, alignment, spacing, imagery and rules group content before adding an enclosing surface. Containers remain appropriate when they express a real relationship or interactive boundary.

State one visual transfer and how it changes this project's composition. Do not copy a reference's branding or substitute its assets for the project's material. Preserve binding facts and assets. Keep the composition recoverable as a separate stage.

## Review then build

Open matching desktop and phone captures. Judge relevance to the brief, reading order, distinctiveness, unnecessary enclosure and how quickly real content becomes reachable. Compare the stated reference transfer with visible evidence. Reject weak composition before investing in wiring; limit revisions to the defects observed. A pleasant screenshot alone is not functional acceptance.

After visual acceptance, implement the required interactions while preserving the accepted visual structure. Test real task states and capture the final result again. Report visual and functional acceptance separately, including remaining subjective weaknesses. Do not call a composition original merely because it differs from the baseline.

For repeatable native CLI work, [the host driven design workflow](autonomous-workflow.md) implements these stages with capture and image-read evidence. A reference receipt must point to a visible decision in the target; reading a screenshot alone does not prove a useful transfer.
